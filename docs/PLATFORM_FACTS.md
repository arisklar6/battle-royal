## sprite-protocol

SUMMARY: BitWorld is a 128x128-pixel retro multiplayer protocol (ScreenWidth/ScreenHeight=128, TileSize=6, legacy 4bpp framebuffer of 8192 bytes) served over WebSocket at ws://localhost:8080 with /player (per-player rendered view with name/slot/token join params), /global (world/spectator view), and /reward endpoints. Sprite v1 is a little-endian binary protocol: server pushes frames via define-sprite (Snappy-compressed raw RGBA, u16 ids/dimensions, optional non-rendering label), define/delete/clear object (i16 x/y/z, u8 layer, u16 sprite id), set-viewport, and define-layer messages; clients send chat text (0x81, u16-length ASCII up to 65535 bytes, printable 0x20-0x7e plus control codes), mouse move/button, a 2-byte 7-bit d-pad+Select+A+B input bitmask (bit 7 masked to 0), a 1-byte ready pacing hint, and debug-sprite overlays that embed server-style messages. The world is larger than the screen: coordinates are i16 precisely to allow off-viewport placement, and the map layer (type 0x00) is drawn in world coordinates and client-zoomable/pannable, with eight screen-anchored UI layer types plus an aspect-preserving full-screen layer 0x09. Draw order is z, then y, then object id, with straight-alpha compositing. There is no text-rendering primitive (text must be baked into sprites) and confirmed no audio support anywhere in spec, code, or README. The 16-color/15-visible palette (code loads a 16-entry palette from an embedded PNG) is a design constraint only â€” the wire format carries full RGBA. Key contradictions where code wins: spec bans layer types above 0x08 yet both spec and code define full-screen 0x09; the mouse-move layer byte is a required field in spec but heuristically optional in the code parser; and the client-message parser silently truncates on malformed input rather than closing as the spec demands.

## replay-format

SUMMARY: The bitreplay format is implemented in src/bitworld/replays.nim and documented (partly stale) in docs/bitreplay_spec.md. The spec doc pins format version 3 with fixed magic "BITWORLD", but the code makes both configurable per game via ReplaySpec (magic, formatVersion, gameName, gameVersion, joinKind, allowChat, allowCompressed, hashOrder). Record types in code: 0x01 tick-hash, 0x02 input (keys bitmask), 0x03 join, 0x04 leave, 0x05 chat, 0x06 debug-sprite, 0x07 raw per-player client-input â€” the 0x07 client-input record, the rjkAddress join variant, gzip/zlib compressed-artifact support, and the rhoStop lenient hash-order mode all exist only in code and are missing from the spec doc. Writer API: openReplayWriter(path, configJson, spec) writes the header (magic, u16 version, gameName, gameVersion, u64 start-ms, configJson string) to a plain File opened with fmWrite; append via writeJoin (two overloads), writeLeave, writeInput, writeChat, writeDebugSprite, writeClientInput, and writeHash (which auto-flushes); finish with closeReplayWriter, plus flushReplayWriter. All writes no-op when writer.enabled is false (empty path yields a disabled writer). Reader API: parseReplayBytes(bytes, spec) validates magic/version/name/version, enforces nondecreasing per-kind timestamps, gates chat on allowChat, and returns ReplayData (joins, leaves, chats, debugSprites, inputs, clientInputs, hashes, configJson); loadReplay(path, spec) is just parseReplayBytes(readFile(path)). There is no URI/network writing â€” disk paths only; compressed hosted artifacts are only handled on read via zippy uncompress. Strings are u16 length-prefixed, byte arrays u32-prefixed, all integers little endian; tickTime/timeTick convert between ticks and replay milliseconds.
